# Bot Media Lifecycle Contract - 2026-10-02

## Status And Boundary

Owner: Codex coordinator. This is the next safety contract after the accepted
[ingest](2026-10-02-bot-inline-media.md) and
[read-only audit](2026-10-02-bot-media-reconciliation.md), not a deployed cleanup
feature. The reference preflight is read-only. No new migration, scheduled
cleanup, Storage deletion or quota refund is enabled by this document.

Ruling: keep reclamation disabled until every reference writer and external-I/O
outcome participates in the same lifecycle. Cost: unused objects remain charged
longer; deleting a referenced object is not an acceptable alternative.

## Proposed State Contract

Keep `private.bot_media_ingests.state` as `reserved | complete`; do not rewrite a
completed receipt into a cleanup status. Introduce a separate object lifecycle
only through a rehearsed, reviewed migration. Proposed lifecycle states:

1. `active`: existing reservation/reference rules continue. Every external PUT
   first records a durable intent tied to object identity and upload generation.
2. `quarantined`: a grace candidate, not deletion permission. All supported
   references and pending external PUTs are rechecked in a fresh transaction.
   Any reference restores `active` before deletion is sealed.
3. `deleting`: no new reference, upload admission, variant publication or lease
   renewal is permitted. Entry requires zero references, no unresolved PUT,
   a fresh verified generation and exclusive object fence. Retry removal; do
   not reopen the object after a DELETE may have reached Storage.
4. `released`: conclusive Storage API removal/absence has been reconciled and
   the retained charge was released exactly once. Identity, fingerprints,
   original charge time and completed result remain immutable tombstones.

Initial grace: 24 hours after the later of last conclusive external-I/O outcome
and last reference removal, never merely `created_at` or the 120-second lease.
Unknown timestamps, malformed metadata, unsupported URL forms, schema drift,
an open moderation hold or overlapping purge claim block reclamation. A second
reference scan after a delay is useful evidence, but is not a writer fence.

Use one object identity `(bucket, path)` and generation. Every DB reference
writer takes its fence, including direct inserts/updates, forwards, bot file
reuse, avatars and variants. Trigger/RPC coverage must be proven against the
live catalog and legacy clients. Missing/unknown URL coverage blocks the
destructive rollout; the preflight's literal URL matching is not that resolver.

No database transaction stays open over network I/O. The `deleting` state seals
DB writers before the external remove. A durable PUT/DELETE intent survives
worker crashes. Expiring a worker lease transfers recovery ownership, but does
not clear an unresolved provider operation or permit quota release. A delayed
old PUT can create bytes after its client times out; retain its hold until the
provider outcome is conclusively reconciled. Grace alone cannot solve this.

Preserve lock ordering: quota lock first for admission/release, operation lock
next where applicable, then object fences in sorted bucket/path order. A
reference writer that takes only object fences must not later acquire quota or
operation locks. Rehearsal must include existing membership, Storage and
message-trigger locks before this order is accepted for a migration.

## Quota And Idempotency

- Never delete the admission/receipt to refund quota. Retained bytes/object
  counts exclude only the exactly-once released charge; rolling 24-hour bytes
  continue using immutable initial `created_at` and `byte_size`.
- Admission and release share the global quota lock. Two reclaimers cannot
  release twice; neither reclaiming nor timeout is a release.
- Preserve token/membership checks. An authorised identical completed retry
  returns the exact original result, including after object reclamation, without
  inserting a message or uploading again. A changed request remains conflict.
- A released incomplete reservation must not be resurrected by the old key.
  Proposed terminal Bot API error: `media_gone`, HTTP 410; this is not shipped
  and must be added/tested in API, SDK and docs together before rollout.
- A new logical send after reclamation requires a fresh object generation and
  new admission. Fingerprint-derived paths currently have no generation; keep
  this incompatible reuse gate closed until the API/storage contract is solved.
- Durable receipt storage and retained media-object limits are different:
  tombstones cannot be pruned under the 24-hour operation-cache policy. The
  current operator cap of 20,000 receipts remains an explicit refusal, not a
  promise that it can report an arbitrarily grown historical ledger.

## Implementation Acceptance Gates

The next destructive slice must first show failing controls for forward/preview,
legacy encoded URL, avatar/variant, moderation hold, old PUT after timeout,
claim lease transfer, stale token/lease and a conflicting existing purge. Then
prove the actual fenced database interleavings, not sequential mocked scans.

Required fault cases: crash before/after sealing; Storage refusal; response lost
after a successful delete; DB failure after Storage success; two claimants;
late PUT completion; new admission exactly at the quota boundary; completed
retry after release. Literal assertions must prove retained quota is released
once while daily bytes and the original result remain unchanged. Unknown
external outcomes hold state/charge and remain operator-visible.

Any migration needs a fresh before-state backup, restore rehearsal, checked
lock/grant/RLS changes, one raising transaction, rollback header and identical
archive. Preserve D-103 deletion behavior while routing bot-owned objects to a
single authority. Rollout starts disabled with a synthetic cohort; no automatic
deletion of the current 21 QA receipts follows from their absent original chats.

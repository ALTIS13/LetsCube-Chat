## External Restore: Решение По Допуску

**Не допущено: Supabase-only restore из текущего offsite и независимая
retention-цель не доказаны.** Read-only на том же LETSCUBE host: прочитаны
только два точных producer-скрипта из `/srv/letscube/scripts`. Наружу вышли
SHA-256 и редактированная форма команд. Скрипты не исполнялись, env и ключи
не читались, прежний blob/репозиторий не открывались.

1. **Единая область шифрования.** Установленный
   `letscube-github-offsite-backup.sh` имеет тот же SHA-256, что и в
   [прежнем inventory](2026-10-18-backup-monitoring.md#state-and-evidence):
   `116eae7fff8b7faf3149f93e17884e3c3a98763d1a1f85e214d81ed9f57cfd71`.
   Он делает `tar -C "$BACKUP_ROOT" -cf - "$backup_name"` для всего
   каталога захвата, передаёт поток в один `age`, затем делит шифротекст.
   [Контракт локального набора](../infra/BACKUP_RESTORE_RUNBOOK.md#backup-scope)
   включает другие компоненты. Отдельного Supabase ciphertext или
   зафиксированного манифеста отдельно извлекаемого компонента нет в
   проверенном контракте. Выбор одного члена tar **после** `age` может
   ограничить запись на диск, но не область расшифрования: он не подходит
   под запрет читать/расшифровывать другие компоненты. Для этого среза
   закрыты и полный extract, и выборочный `age | tar`.
2. **Внешняя история не закреплена.** GitHub producer использует force-push;
   проверенный commit доказывает доступность ciphertext на момент того
   чтения, а не защищённые старые версии или контроль ключа при потере хоста.
   `letscube-offsite-backup.sh` (SHA-256
   `f14b4ce199b1fe473ecf7d9c04996c36c853184f884af129c8015e7ecea7dbc9`)
   передаёт весь `backup_dir` в rclone/restic/Borg. Ранее принятый
   [redacted inventory](2026-11-05-task4-external-backup.md) не нашёл
   destination keys, timer был выключен. Это не свежая проверка конфигурации,
   и ни имя репозитория, ни наличие инструментов не задают отдельную цель
   LETSCUBE, защищённые версии, срок хранения или доступ при потере сервера.
3. **Нет closure для этого захвата.** Принятый
   [D-342 sealed-only restore](2026-10-18-production-completion.md#d342-sealed-only-package-restore-1537z)
   подтверждает другой, явно запечатанный пакет. Он даёт проверенный
   метод сравнения, но не манифест, роли, дополнения, контрольные хеши или
   ключ восстановления для внешнего snapshot от 5 ноября.

## План Изолированного Восстановления

План не выполнялся. Все гейты обязательны по порядку; на первом несовпадении
остановиться, сохранить только код отказа и обезличенные метаданные.

1. **Граница пакета.** Сначала нужен отдельно зашифрованный набор
   LETSCUBE Supabase с фиксированным ID захвата и внешним доверенным хешем
   или подписью манифеста. Для DB-only: exact custom dump, роли и
   необходимые дополнения/эталоны того же захвата. Подтвердить ACL,
   настройки, расширения, данные и последовательности; не подставлять
   дополнения из D-342 или живой БД. Для восстановления всего Supabase
   отдельно потребуются байты Storage с привязкой к тому же checkpoint,
   функции и разрешённая конфигурация/секреты из отдельного escrow. SQL
   metadata Storage не заменяет его объекты. Новому пакету не присваивать
   статус принятого GitHub blob от 5 ноября.
2. **Независимый вход.** Закрепить внешний объект и его неизменяемую версию,
   размеры и SHA-256 частей в точном порядке и итогового ciphertext,
   fingerprint получателя, capture ID и watermark. В отдельном допуске
   подтвердить read-only доступ и наличие подходящего recovery key без
   production host, его deploy key и GitHub push-доступа. Ключ не выводить,
   не брать из старых хостовых скриптов. Пока этого нет, не скачивать и
   не расшифровывать ничего. В будущей проверке сначала сверить шифротекст;
   затем для **Supabase-only** пакета проверить успешную аутентификацию
   `age` до EOF, точный allowlist путей, размеры и SHA-256 всех
   членов. Не принимать лишние/повторные пути, traversal, ссылки или
   специальные файлы. Не запускать SQL или код из пакета до сверки.
3. **Точная цель и restore.** Только новый изолированный Supabase PG17
   совместимого pinned build с проверенными расширениями, отдельным
   data dir и локальным Unix socket; сеть и все исходящие dispatch
   (`pg_net`, cron, webhooks) отключены до первой записи. Проверить
   точный CID/cluster/пустой prestate и отсутствие любых prod fallback.
   Сверить CUSTOM header/watermark и допустимый TOC. Применять роли и
   capture-matched prerequisites, затем `pg_restore --exit-on-error` и
   проверенные дополнения в точном порядке; не ослаблять ACL/RLS.
   Ошибка, неожиданный объект или дрейф цели запрещают продолжение.
4. **Критерий фактического восстановления.** Независимый readback
   сравнивает с эталоном этого же пакета владельцев, роли/ACL/RLS,
   schema/constraints, расширения, контрольные хеши данных и
   последовательностей. Проверить, что запрещённый локальный доступ
   остаётся запрещённым. Нужны exit status, сверка хешей, длительность,
   точный cleanup временной БД и plaintext; выводить только редактированный
   receipt. Один `pg_restore --list`, exit 0 или совпадение времени
   не считаются фактическим restore.
5. **Отдельная retention-приёмка.** Владелец закрепляет отдельный
   LETSCUBE Supabase namespace и failure domain, требуемый срок/политику
   неизменяемых версий и независимых хранителей read/recovery. Producer
   не должен иметь возможность удалить, перезаписать или сократить срок
   уже сохранённого объекта. После отдельного допуска подтвердить
   как минимум две версии: новая опубликована, прежняя остаётся
   независимо читаемой с ожидаемым хешем и сроком хранения. Отказ
   overwrite/delete проверять только на отдельном синтетическом объекте.
   Для RPO нужна серия привязанных capture-to-readable водяных меток и
   критерий последней восстановимой транзакции; один успешный restore
   или срок хранения сами по себе RPO не задают.

Следующий конкретный вход для проверки: подписанный или независимо
закреплённый Supabase-only манифест, точный идентификатор независимого
хранилища/версии и подтверждённый recovery custodian. Без них офлайн
restore остаётся закрыт. В этом срезе не было расшифровки, передачи
backup payload, восстановления или изменений на production.

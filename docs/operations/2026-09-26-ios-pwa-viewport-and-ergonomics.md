# iPhone Home Screen PWA: viewport and chat ergonomics (2026-09-26)

Owner: separate iOS/MacOS chat. Current stage: revised iOS viewport code verified in source and synthetic browsers and deployed on the public web origin; physical iPhone acceptance remains separate. Source: tester screenshots of the installed iPhone 15 Pro Max PWA, current iOS runtime/styles, and WebKit's public [Home Screen viewport bug 301994](https://bugs.webkit.org/show_bug.cgi?id=301994). Do not copy private chat content into this record.

## First pass (`4fa03dc9`)

The installed shell previously replaced its `100vh` height with `visualViewport.height` even while the keyboard was closed. In the original WebKit fixture, a 932 px standalone viewport with a 872 px visual viewport then rendered a 872 px shell. The first pass retained `100vh` at rest and used the visual viewport only with the keyboard. It also raised the installed iPhone chat header title to 17 px, list title/preview to 16/14 px, and primary chat/composer touch targets to 48 px. The message body retained the 16 px default and the user's size setting; Liquid Glass and other platforms stayed unchanged. Its 24-case viewport matrix, safe-area cases, relevant unit checks, typecheck and fixture build passed. The public site subsequently served this pass, but that cannot prove what code was executing in an already-open installed PWA.

## Follow-up: the lower edge is not paintable

Two subsequent 1181×2560 screenshots map to about 430×932 CSS pt. Both cut the page at y≈873 pt and show a uniform ≈59 pt lower strip. The chat-list navigation starts at y≈834 pt, exactly where a 932 pt `100vh` shell places a 90 pt capsule with an 8 pt bottom gap; the capsule is clipped at 873 pt. The composer is cut at the same line. These measurements establish a layout/paintable-height mismatch, not by themselves the iOS version or the installed bundle hash.

At the time of the check, public `https://app.letscube.ru/` served `/assets/index-BDlGRmCT.js`, `/assets/index-B2gb4PcC.css`, and service-worker build `0768477fe5413f1c`, all with the first-pass code. The Home Screen document may still have held older JS/CSS until navigation or relaunch. WebKit bug 301994 independently reports a similar standalone-only split on iOS 26.5.2: `screen.height` exceeds `innerHeight`, `100dvh` and `visualViewport.height` by 62 px, and the extra strip is outside DOM paint. It was later confirmed again in an iOS 27 beta. This is a strong mechanism match, not an on-device measurement of LETSCUBE.

The scoped correction fits `--kub-app-height` to `window.innerHeight` before React's first paint, with `100dvh` as the CSS fallback, and `PwaRuntime` keeps that measurement current at rest. It still uses `visualViewport.height` while a keyboard actually reduces the viewport. A keyboard-open rotation cannot reset the resting height to its shrunken value and lose the pan compensation. Therefore a merely short visual viewport does not shrink an otherwise full canvas, while a short paintable canvas no longer puts navigation or composer beneath its edge. The Safari tab and Android/Windows/desktop paths are unchanged. If the strip is truly system-owned, the page cannot paint it away; the correction makes controls visible and tappable above it.

The new WebKit fixture models `100vh=932`, `innerHeight=visualViewport.height=873`, and a blocking 59 pt system strip. Before the correction its shell measured 932 instead of 873 and the test failed; afterward navigation, composer, keyboard open/dismissed, and hit-testing passed in light and dark themes. Separate cases failed before and passed after fitting the first frame before the React entry and preserving the header pan on keyboard-open rotation. The final installed-viewport matrix passed 36/36 in Chromium and WebKit; the WebKit safe-area portrait/landscape matrix passed 22/22, and Chromium's three inset checks passed on rerun (one earlier CDP inset override returned zero in landscape before rerun). The source unit guard, web typecheck and fixture production build passed. Synthetic 430×932 and 1440×900 pixels were inspected in both themes; they are not a physical iPhone proof.

Deployment proof: the shared checkout's scoped PWA files were included in `c057d768` and pushed to `main`. The healthy web image tag is `c057d76885c5e74345d0c04eb35996bea49622d2`. Public HTML referenced `/assets/index-D2u4L-hb.js` and `/assets/index-DvWgWwAy.css` in five consecutive reads and contained the new pre-React `innerHeight` boot measurement. Public JS contained the runtime height token and `innerHeight`, public CSS had the `100dvh` token without the standalone `100vh` override, and `sw.js` build `c2564426622aeadd` precached those exact assets. During Coolify's short overlap of old and new web containers, requests for the new CSS alternated 200/404; after the old image exited, five consecutive CSS reads returned 200. This is deployment evidence, not proof of the installed PWA's currently open document.

Remaining gate: have the tester fully close and reopen the installed PWA while online, without reinstalling it, and check list/composer with keyboard closed/open in both themes. If possible, record iOS version and privacy-safe geometry (`screen.height`, `innerHeight`, `visualViewport.height`, computed `--kub-app-height`, and navigation/composer bounds) plus loaded versus public asset filenames. No chat content is required. Only that device check can tell whether the lower strip itself is an OS-owned Home Screen limitation on this phone.

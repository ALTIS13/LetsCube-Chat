# PocketFlow — эталонный бот, и аудит платформы, который он заказал

Запрошено владельцем 2026-09-19. Документ отвечает на первую половину задания
(«Начни с аудита текущей Bot Platform и существующего examples/SDK») и
предлагает план на вторую (P0).

Всё ниже прочитано в коде и в применённых миграциях, а не в документации.
Там, где документация расходится с кодом, это названо отдельно.

## 1. Что публичный Bot API есть на самом деле

Один маршрут: `POST https://api.letscube.ru/bot/v1/<method>`, JSON внутрь и
`{ok: true, result}` наружу, `{ok: false, error: {code, message, request_id}}`
при ошибке. Кроме него у шлюза есть только `/healthz` и
`/bot/manage/v1/*` — последний для самого приложения LETSCUBE, а не для
программы бота.

**Семнадцать методов, полный список** (`artifacts/api-server/src/bot/schemas.ts`):

| группа | методы |
|---|---|
| идентичность | `getMe`, `getWebhookInfo` |
| сообщения | `sendMessage`, `sendPhoto`, `sendVideo`, `sendDocument`, `sendVoice`, `sendChatAction` |
| правка | `editMessageText`, `deleteMessage` |
| файлы | `getFile` |
| команды | `setMyCommands`, `getMyCommands` |
| кнопки | `answerCallbackQuery` |
| доставка | `setWebhook`, `deleteWebhook`, `getUpdates` |

**Четыре типа Update**: `message`, `edited_message`, `callback_query`,
`membership`. Больше нет ничего.

`getUpdates` возвращает `{...payload, update_id}` — то есть на верхнем уровне
форма Telegram, `{update_id, message: {...}}`. Внутри — нет.

## 2. Где принцип «тот же код против Telegram» ломается

Владелец поставил его как ключевой: «с заменой только BOT_API_BASE_URL,
BOT_TOKEN и environment-specific configuration». **Сегодня он не выполняется, и
дело не в наборе методов, а в форме провода.** Четыре расхождения, каждое
структурное:

| | LETSCUBE | Telegram |
|---|---|---|
| идентификаторы | `chat_id`, `message_id`, `reply_to_message_id` — **UUID** | 64-битные целые |
| медиа при отправке | `media: {bucket, object_path, mime_type, size_bytes}` | `file_id` / URL / multipart |
| идемпотентность | `idempotency_key` **обязателен** у каждого пишущего метода | отсутствует |
| время | `date` — строка timestamptz | unix-секунды |

И объект сообщения назван иначе: у нас `id`, `from.display_name`,
`attachment.{file_id,kind,mime_type,…}`, `chat.name`; у Telegram —
`message_id`, `from.first_name`, `photo[]`/`document{}`, `chat.title`.

**Вывод, который я не могу обойти:** «один и тот же исходный код» достижим
только через адаптер транспорта — тонкий слой, который прячет форму провода за
одним интерфейсом, а бизнес-логика PocketFlow пишется против него. Это ровно
то, что владелец допустил словом «по возможности», и это не отговорка: адаптер
и есть проверка совместимости, потому что он делает расхождения явными
списком, а не рассказом.

Платформу при этом не переписываем — §21 задания и так это запрещает.

## 3. Gap register: чего для P0 нет в API

Каждый пункт — «что нужно PocketFlow / что есть / чего стоит закрыть».
Ничего из этого я пока не чиню: сначала фиксация, как велено заданием.

**G-1. Бот не может отправить файл. Вообще.**
`sendPhoto` и соседи требуют `object_path` в `chat-media` длиной 80–1024
символа, и перед отправкой шлюз вызывает `bot_upload_authorize_internal`,
который **требует, чтобы объект уже лежал в `storage.objects`** — иначе
`bot_upload_object_missing`. То есть метод отправляет уже существующий объект,
а не загружает новый.

Ни одного пути положить байты у бота нет:

- метода загрузки в публичном API нет — единственный публичный маршрут это
  `POST /bot/v1/<method>` с семнадцатью именами, и загрузки среди них нет;
- `getFile` отдаёт `file_id`, `mime_type`, `file_name`, `file_size` и
  подписанную ссылку на 60 секунд, но **не отдаёт `object_path`**, так что бот
  не может переслать обратно даже тот файл, который ему только что прислали;
- таблица `private.bot_upload_grants` существует и выглядит как механизм
  загрузки (грант живёт ≤15 минут, гасится отправкой), но **ни одна политика
  `storage.objects` на неё не ссылается** — грант ничего не открывает, он
  только записывает факт.

Значит вычёркиваются §7 (File Tools) целиком и QR из §3. Документация говорит
«Отправка ранее разрешенного объекта chat-media» — формулировка честная, но
описывает возможность, у которой нет входа.

**Минимальное исправление, которое я предлагаю:** разрешить
`sendPhoto`-семейству принимать `file_id` (идентификатор сообщения, которое
боту и так разрешено читать) вместо storage-ссылки. Это ровно модель Telegram —
там пересылка файла делается именно `file_id` — так что исправление **повышает**
совместимость, а не понижает; путь в хранилище при этом наружу не выходит.
Отдельный вопрос — загрузка новых байтов (QR, конвертация); она требует
настоящего метода загрузки и в минимальное исправление не помещается.

**G-2. Inline mode отсутствует.** Нет `inline_query`, нет
`answerInlineQuery`, нет `chosen_inline_result`. §8 задания и пункт P0 «inline
mode» нереализуемы. Сам владелец оставил оговорку «если он поддержан
платформой» в критериях приёмки (§22.11) — она срабатывает.

**G-3. Опросов нет.** Нет `sendPoll`, нет `poll`/`poll_answer`. §10 и `/poll`
из §9 нереализуемы через Bot API. Fallback, который задание само предлагает
(сообщение плюс inline-кнопки), возможен и будет использован.

**G-4. Нельзя изменить только разметку.** Есть `editMessageText`, который
принимает `reply_markup`, но нет `editMessageReplyMarkup`. Практически это не
блокирует §2 («editMessageText/editMessageReplyMarkup вместо новых
сообщений»), потому что текст можно переслать тот же; но это лишний трафик и
расхождение с Telegram, которое selftest обязан показывать как UNSUPPORTED, а
не прятать.

**G-5. `parse_mode` отсутствует, а форматирование всё равно применяется.**
Клиент `formatText.tsx` сам размечает `bold`, `italic`, `code`, `strike`,
ссылки и упоминания в любом тексте. То есть бот не может отправить текст со
звёздочками буквально, и не может выключить разметку. Для §3 (Pretty JSON) и
§7 (SHA256) это имеет значение: вывод кода надо оформлять так, чтобы клиентский
токенайзер его не портил, и это надо проверить на пикселях.

**G-6. Ничего из P1/P2/P3 не существует**: реакций, тем-топиков как Update,
Rich Messages, streaming, ephemeral, Mini Apps, Business/Guest/Bot-to-Bot,
платежей — нет ни одного метода и ни одного типа Update. (`topic_id` в
сообщениях есть и принимается при отправке — это единственный след темы.)
Selftest обязан отмечать это как UNSUPPORTED и не как FAIL: неподдержанное и
сломанное — разные вещи, и задание это прямо требует (§22.13).

**G-7. SDK и examples не существуют.** В репозитории нет ни одного каталога
`sdk/`, `examples/` или эквивалента; единственный «пример» — два фрагмента
(JS и Python) в `artifacts/kub/src/content/botApiDocs.ts`, которые показывают
один вызов `fetch`. Аудит «существующего SDK/examples» из задания поэтому
отвечает: **аудировать нечего, PocketFlow будет первым потребителем API
снаружи**. Это делает его ценнее как тест — и означает, что часть его
транспортного слоя логично оформить как первый настоящий SDK.

## 4. Что из P0 строится сегодня полностью

Без единого изменения платформы:

- приватный чат с ботом, `/start` и команды (`setMyCommands` есть);
- текст, `reply_to_message_id`, `sendChatAction`;
- inline-клавиатуры и `callback_query` + `answerCallbackQuery`;
- `editMessageText`, `deleteMessage`;
- polling и webhook — оба транспорта настоящие, `setWebhook` требует HTTPS и
  `secret_token`, у `getUpdates` есть long-poll с таймаутом до 30 с;
- persistent state, reminders, scheduler — это целиком сторона PocketFlow;
- generic external webhook (§5) — тоже целиком сторона PocketFlow;
- URL watcher (§6) с SSRF-защитой — тоже;
- группы: бота теперь можно добавить в групповой чат (D-235, закрыт сегодня),
  и `membership` приходит как Update;
- `/selftest` — и именно он делает всё вышеперечисленное проверкой, а не
  демонстрацией.

**Приём файлов** работает: `attachment` приходит в Update, `getFile` даёт
ссылку на 60 секунд, так что «показать dimensions/MIME/размер/SHA256» из §7
выполнимо. Не выполним только **обратный** путь (G-1).

## 5. Архитектура

§21 задания требует разделения, и оно же диктует размещение.

```
artifacts/pocketflow/          новый workspace-пакет
  src/
    transport/                 адаптер Bot API — единственное место, знающее форму провода
      letscube.ts              наша реализация
      types.ts                 нейтральный интерфейс (Chat, Message, Update, Keyboard)
    app/                       бизнес-логика: inbox, saved, reminders, watcher, webhooks
    http/                      входящие: /hook/<id>, healthz
    scheduler/                 фоновые задания
    store/                     persistence
```

Транспортный интерфейс — это и есть ответ на §22.17: чтобы тот же бот пошёл
против Telegram, добавляется `transport/telegram.ts`, а `app/` не меняется.
Писать сам Telegram-адаптер в первой версии не нужно; нужно, чтобы граница
существовала и была проверена тестом, который прогоняет `app/` против
поддельного транспорта.

Конфигурация — переменными окружения, как просит §18:
`BOT_TOKEN`, `BOT_API_BASE_URL`, `PUBLIC_BASE_URL`, `TRANSPORT`,
`DATABASE_URL`, `DEVELOPER_IDS`, `WEBHOOK_SECRET`.

**Persistence.** PocketFlow — приложение стороннего разработчика; лезть в схему
мессенджера ему нельзя. Своя схема в своей базе.
